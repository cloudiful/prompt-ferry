# 端点 Key 持久化

端点保存会将自己的行与 API Key 集合作为一个整体写入。本指南说明这一保证的内容、保存实际会向 Key 表写入什么，以及 Key 删除相关索引在运维层面的含义。

## 原子性

`create_endpoint`、`create_endpoint_with_mcp` 与 `update_endpoint` 运行在同一个事务上。更新会先对端点行取 `FOR UPDATE` 锁，再读取 Key 集合，因此：

- 同一端点的两次重叠保存会串行执行。后一次会等待前一次完成，而不会基于前一次尚未写完的行来规划写入。
- 用于构造返回端点的读取发生在同一事务上，因此响应描述的是本次保存写入的行，而不是更晚的状态。
- 无法存储的请求不会留下任何痕迹。端点行、新名称与 Key 集合会一起回滚，被拒绝的创建也不会插入端点。

创建操作不需要额外加锁：它自身的插入已经在整个事务期间持有了新的父行。

存储层返回之后处理器的后续工作——OAuth 与托管 MCP 的副作用——在该事务之外，不属于这一保证的范围。

## 保存实际写入的内容

保存会将已存储的 Key 集合与请求的集合进行比较，只执行差异所隐含的语句：

| 变化 | 语句 | `updated_at` |
| --- | --- | --- |
| 无变化 | 不执行 | 保持不变 |
| 标签、密钥或启用标记 | 更新 | 推进 |
| 仅位置变化 | 先重编号，再还原 | 保持不变 |
| 新增 Key | 插入 | 新行 |
| 删除 Key | 删除 | 行消失 |

其中两点值得明确说明。未变化的 Key 完全不会被写入，因此保存一份未作改动的表单不会让它变旧。Key 集合重排并非对任何 Key 的编辑，因此重排会移动位置而不会推进任何一个 `updated_at`。

请求携带 `key_id` 时按 `key_id` 标识 Key，否则按 `key_label` 标识，因此未提供 `key_id` 的客户端仍会保留其所指 Key 的标识与创建时间。已不再存储的 `key_id`（可能是并发保存替换掉了它）会回退到标签匹配；若标签也是新的，则按新插入处理。正是这一点避免了陈旧请求失败或丢失 Key。

重排会先把所有位置发生变化的 Key 移开，再将它们还原到请求的位置，因此循环换位不会把两个 Key 送到同一个槽位。位置或 Key 声明发生冲突的请求会在执行任何语句之前被拒绝。

## Key 删除与外键索引

`usage_charges.endpoint_key_id` 与 `conversation_endpoint_overrides.endpoint_key_id` 都是指向 `endpoint_api_keys` 的外键，动作为 `ON DELETE SET NULL`。删除一个 Key 需要找出所有引用它的行，这两列都配有专门用于该查找的索引：

- `idx_usage_charges_endpoint_key_id`
- `idx_conversation_endpoint_overrides_endpoint_key_id`

删除 Key 仍会保留其数据行。引用会被置为 NULL，因此计费记录与其历史依然保留，只是归属于端点而非某个 Key。

`request_records` 不存在指向 Key 表的外键，因此刻意未为其建立相关索引。

### 索引运维

两个索引都通过 sqlx 的 `-- no-transaction` 指令以 `CREATE INDEX CONCURRENTLY` 构建。PostgreSQL 拒绝在事务块内执行 `CONCURRENTLY`，而 sqlx 会把一个迁移文件作为单个批次发送，因此每个迁移只包含一条语句——正因如此，两个表对应两组迁移。

对运维人员而言，其后果是：并发构建失败后会留下一个存在但无效的索引。PostgreSQL 不会使用它，必须人工检查并修复或删除。测试校验的是有效性而非是否存在，因为目录中出现一个名字并不能证明该索引可用。应用不会删除并非由它创建的索引。

将任一迁移应用到生产环境需要运维批准并预留窗口。索引构建本身在构造上是在线完成的，但发布流程不属于本代码库的职责范围。

## 验证

`tests/endpoint_key_fk_baseline.rs` 会测量在给定数据库上删除一个 Key 的开销，并打印所选择的执行计划，从而可以在索引存在前后对同一指标进行测量。它只报告耗时，不以耗时作为通过条件：基于时间的断言会把机器的状态变成测试失败。它同时会打印测量时的状态（包括当时存在哪些索引），因此后续运行不会被误读为先前的运行。
