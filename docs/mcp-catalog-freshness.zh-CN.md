# MCP 目录新鲜度

Worker 为每个已配置的 MCP server 保留一份 MCP 目录快照：该 server 上次被访问时声明的工具、资源、资源模板和提示词。本文档说明一份快照可以对外提供多久、单个 server 的刷新由谁负责，以及缓存不做哪些事情。

## 一份快照上的两个时钟

每份已存储的快照都带有两个互相独立的时间戳：

- 快照所属的 server **配置代次**。配置发生变化（URL、transport、凭据、过滤规则）会产生新的代次，旧代次的快照绝不会被对外提供。
- **获取时间**：快照从上游取回的时刻。这是唯一决定快照能否继续对外提供的时钟。

两者绝不混淆。读取快照不会推进获取时间，因此旧快照不会因为被读取而变新。获取时间字段出现之前写入的旧负载没有该时间戳，这类负载被视为过期，而不是新鲜。

## 新鲜度状态与默认值

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| `missing` | 当前配置代次没有快照 | 读取会执行一次有界刷新 |
| `fresh` | 少于 5 分钟 | 直接对外提供，不发起任何上游调用 |
| `stale` | 5 分钟到 30 分钟之间 | 对外提供，同时恰好运行一次刷新 |
| `expired` | 超过 30 分钟 | 绝不对外提供；读取必须先恢复目录 |

软新鲜窗口（5 分钟）和最大对外提供时长（30 分钟）是生产默认值。Local、Valkey 和 SQLite 后端执行同一套策略，因此无论由哪个后端存储，快照的寿命一致。

存储保留期与新鲜度相互独立。已存储的快照活得比它可以被对外提供的时刻更久：Valkey 条目按配置的 Valkey 保留窗口过期，SQLite 条目在 standalone 协调存储中按同一窗口过期。保留期决定字节何时被丢弃，新鲜度决定内容何时可以被对外提供。

## 每个缓存一个协调器

有界刷新状态属于目录缓存，而不是单个 service 实例。共享同一份运行时缓存的全部读取、管理端手动刷新、启动批量加载和周期性刷新因此共享同一个刷新协调器：

- 一个归属许可限制的是实际的刷新工作，而不仅是外层读取循环的 future。对多个过期目录的一次批量读取绝不会超过配置的刷新并发数，共享同一缓存的多个 service 包装也共享同一上限。
- 后台刷新按 server 与配置代次合并，因此同一个 server 的重复过期读取只会排队一次刷新，而不是每次读取各一次。该上界统计全部未完成工作（含已被取代的代次），因此配置反复变更不会堆积出无界的等待队列；超出的突发工作由下一轮刷新重试。
- 每个公开读取与手动刷新本身都是被跟踪的操作，而不只是派生出的刷新任务。每个操作在任何缓存或仓库调用之前就取得一个绝对截止时间与一个活动计数，该截止时间覆盖缓存查询、归属许可、租约、仓库校验、上游抓取与发布。跟随者遵守同一截止时间与同一取消信号。
- 取消由协调器统一负责，并且在缓存、仓库或后端等待进行中即可被观察到，而不只是在轮询之间。受管理任务先停止调度，再在有界超时内排空全部被跟踪活动，因此关闭会取消冷读取跟随者、读取触发的刷新、批量预热与周期任务。被取消的归属者会在预留的释放余量内显式释放租约；租约过期只是恢复路径。
- 即使调用方被中止，租约清理仍保留在统计中。被跟踪操作守卫采用引用计数，并有一个克隆移入租约，因此抓取中或释放中被丢弃的调用方 future 会一直保持其活动对排空可见，直到有界清理结束。协作式释放会保留归属令牌直到后端确认完成，因此被取消的释放会移交清理责任，而不是静默消耗令牌。超出余量的清理会记录该租约只能由过期恢复，而不会声称已确定性释放。

## 每个 server 只有一个刷新归属者

对某个 server：

- 同一时刻只有一个 worker 刷新它。Valkey 通过 `SET NX EX` 决定归属，并用带令牌的比较删除释放租约，因此已经过期并被其他 worker 接管的租约不会被误删。standalone SQLite 后端复用协调器租约及其归属令牌。内存后端没有共享协调能力，退回到进程内 single-flight 注册表，其槽位同样携带归属令牌，只能在单个进程内去重。
- 租约有效期始终覆盖整个获取过程（不含许可等待）并留有安全余量，因此租约不会在刷新仍在进行时过期。被取消的刷新会显式释放租约；若该释放无法执行，由有界的租约过期来恢复。
- 取得租约后，worker 会先重新读取已存储的快照再决定是否发起上游请求，因此两次读取不会对同一个 server 重复抓取。
- 快照发布前会重新核对配置代次，并以抓取前捕获的确切信封为基准，通过后端比较交换（CAS）提交发布。属于已被取代配置的快照不会发布，已被失效的条目也不会被仍在运行的抓取复活。
- 失效是共享且原子的栅栏。SQLite 复用协调器的 `get_or_insert`/`replace_if_current` 原语；Valkey 使用负载安全的 Lua 比较交换，并沿用相同的保留策略。被失效的条目以带修订号的墓碑表示，而不是删除键，因此持有旧信封的发布者比较失败，且不会改动共享存储。读取方把墓碑视为缺失并清除本地副本，因此对端无法提供已失效的数据。本地后端在自身锁下执行等价的修订比较。
- 共享后端读取失败时按失败关闭处理。当 Valkey 或 SQLite 权威不可用时，缓存不会回退到进程内副本，因为该副本当前的修订状态未知：对端可能已经将其失效。这类读取会把目录报告为缺失，恢复时在共享基准处失败，因此受影响的请求得到可操作的 “catalog is not ready” 错误，而不是可能已失效的 schema。这是有意的可用性取舍：仅本地后端继续从内存提供，而权威不可达的共享后端宁可报错也不提供过期数据。
- 读取若找不到可用快照，会等待其他 worker 正在进行的刷新，随后要么提供已发布的结果，要么返回可操作的错误。过期快照绝不会作为兜底被对外提供。
- 每次发布都携带一个发布标识，即使内容未变也会重新生成。跟随其他归属者的强制刷新只有在观察到比其在尝试归属前所见的更新的发布后才算成功，绝不会把刷新前的快照当作刷新结果返回。内容指纹与发布标识、获取时间保持独立。

## 启动与周期性刷新

`mcp_warmup` 保留三种模式：

- `all`（默认）在启动时加载每个已启用 server 的目录。
- `lazy` 和 `off` 跳过批量冷启动，它们的目录由需要它的读取来加载。

与模式无关的是，受管理的周期性刷新每 60 秒运行一次，并带最多 10% 的随机抖动。它刷新已经存在且不再新鲜的目录，并且绝不会冷加载从未抓取过的目录。该刷新在连接态和 standalone worker 中都运行，关闭时会被取消，并会取消进行中的上游抓取而不是等待它结束。standalone 的请求路径、管理端状态与该受管理任务共享同一份缓存，因此共享同一个协调器。

## 失败处理

刷新失败会保留上一份快照用于诊断，但不会延长它的获取时间，因此失败的刷新无法让旧快照重新变得可对外提供。有界退避只抑制同一配置代次的下一次后台尝试，因此配置变更不会被旧代次的失败记录挡住。当目录无法恢复时，管理端目录接口返回 `mcp catalog is not ready` 与服务不可用状态；MCP 代理向客户端报告同样的情况。

## 限制

- 缓存刷新的是 worker 所提供的内容。它无法更新客户端已经持有的 schema：缓存了输出 schema 的客户端会一直使用它，直到再次执行 `tools/list`。schema 变化不会向客户端发送任何通知。
- 刷新不会重放工具调用，不会扩展 schema，也不会修改结果。针对旧 schema 被接受的调用不会自动重试。
- 目录是从上游读取的声明。worker 不会用工具之后返回的结果去校验该 schema。
- 发布栅栏通过 `updated_at` 发现配置行变化，并通过共享信封发现并发发布或失效。若原地修改保持相同的 `updated_at` 且未触碰目录信封，则该栅栏无法发现。
