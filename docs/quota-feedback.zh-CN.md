# 配额反馈与汇总

端点套餐用量响应会提供可选的逐 Key `quota_status` 元数据，作用范围为 `text_inference`，状态包括 `available`、`exhausted`、`unknown`、`cooling`、`rate_limited` 和 `upstream_unavailable`。详情视图仍保留原始 provider 窗口、余额、模型行及观测历史。

## 状态说明

- `available` 需要来自新鲜成功观测的默认文本可用额度。
- `exhausted` 表示适用的额度或余额约束已确认耗尽。重置时间已过的 0 不会被视为当前耗尽。
- `unknown` 表示额度信号缺失或不受支持、观测过期、刷新失败，或 0 值的重置时间已过。未知既不是 0，也不能证明额度可用。
- `cooling` 表示 Key 或端点因额度或余额确认耗尽而被临时排除。响应会在可用时提供冷却截止时间；截止后可进入受控恢复探测。
- `rate_limited` 表示 Key 因限流、并发限制或进行中的额度预留而被临时排除，账户额度本身没有减少。
- `upstream_unavailable` 表示上游明确表示当前无法服务该请求。

只有确认耗尽才会得到 `cooling` 或 `exhausted`。仅出现 quota、credit、billing、token plan 等字样，或单独的 HTTP 429、402，都不构成耗尽证据；响应体无法解释的 429 会记为 `rate_limited`。

这些状态描述默认文本推理，而非所有模型或模态。MiniMax 汇总仅使用 `general` 模型行；视频等独立模型窗口仍会显示，但不会增加文本汇总。余额类 provider 保留原生单位，不合并不同币种；DeepSeek 可用性以 provider 的 `is_available` 标志为准。

## 有效徽标与详情

端点徽标会对短期和长期窗口使用相同的、已确认可用 Key 集合计算平均值。已确认耗尽或额度冷却的 Key 不会抬高汇总。被限流或上游暂不可用的 Key 额度未受影响，因此仍按其上报窗口参与平均，并在这些百分比旁显示对应的临时状态徽标。所有适用 Key 均确认耗尽时，对应汇总为 0；只有部分 Key 已知时会标记为部分可用。新鲜度或适用性未知时，徽标会如实显示未知，而不会把缺失信号表示成可用或 0。

只要还有一个 Key 可用，通道就保持可用，不会被其他被阻断的 Key 遮盖。只有当所有 Key 都被阻断时，端点才按现存最明确的原因展示，优先级依次为额度冷却、上游暂不可用、限流；它不会声称所有 Key 均已耗尽。

详情视图保留所有上报的 Key、模型、窗口、余额、重置时间和历史行。逐 Key 状态徽标是附加信息，不会替换或改写 provider 数值。提示信息中可查看观测时间、刷新失败和下次重试时间。已经过去的截止时间会显示为未知，直到下一次刷新为止，因此已结束的退避不会仍显示为进行中。

## 刷新与范围

配额刷新会保留最近一次成功的原始观测，同时将刷新失败或过期观测标记为未知。后续成功刷新会恢复当前状态。OpenAI ChatGPT 订阅状态使用持久化观测时间和新鲜度规则，详见[配额快照](quota-snapshots.zh-CN.md)。

同一 Worker 进程中克隆的状态共享配额冷却反馈和套餐缓存。不同 Worker 不会即时共享冷却或反馈记录，因此各自观测和刷新收敛前可能显示不同状态。仅序列化配额元数据不会触发 provider 请求。

## 内置 MiniMax MCP 工具

内置的 `web_search` 与 `understand_image` 工具与 AI 路由复用同一配额缓存和同一逐 Key 反馈存储，因此在同一 Worker 进程内两条链路看到同一配额状态。托管（PostgreSQL）Worker 会把该共享缓存提供给内置工具。独立（SQLite）Worker 完全没有配额快照来源，因此那里的内置工具在没有快照的情况下运行：它们在已启用的 Key 之间分散，并依据实际收到的响应作出反应。这两个工具是只读的，因此遇到配额或限流拒绝时可以切换到另一个端点 Key。

`web_search` 计入 `general` 配额组，因此缓存的 general 快照会筛选它的候选 Key：已确认剩余额度为 0 的 Key 在仍有可用 Key 时不会被调用。未知或过期的快照是"无信号"而非"已耗尽"，这类 Key 仍可被选中，并使用中性权重。图像工具计费的分组 provider 并未公开说明，因此不会推断任何分组：它在已启用的 Key 之间分散，并依据实际响应作出反应。图像选择同样从不读取该共享状态：某个 Key 上的搜索耗尽、限流冷却或进行中的恢复探测都不会把它移出图像候选池，也不会改变它的权重。图像结果既不会写入也不会清除共享的 general 配额反馈，也不会占用共享的恢复探测，因此图像成功或图像 429 都不会抹掉搜索侧记录的耗尽，搜索侧仍按自身状态评估该 Key。

候选 Key 是已启用且非空的 Key 行。旧的内嵌端点 Key 仅在端点完全没有 Key 行时使用：当存在 Key 行但全部已禁用或为空时，端点没有可用凭据，不会发出任何请求，尽管常规端点保存会从第一行推导出该旧字段。

一次调用最多消耗三次上游尝试，即首次尝试加两次切换，且每个已启用的 Key 最多尝试一次。每次尝试前都会重新评估候选 Key，因此在调用期间变得不可用的 Key 会退出候选。报告额度耗尽的 MiniMax 业务码和 HTTP 429 会切换到下一个 Key；429 冷却会遵循有上限的 `Retry-After`，同时不会用完调用方的整体预算。认证或参数校验失败、服务端失败、载荷格式错误和传输失败都会直接返回给调用方，不会自动重放；未启用 Key 负载均衡的端点保持其单个已配置 Key。成功的 HTTP 状态本身并不等于成功调用：无法读取或非 JSON 的响应体，以及不符合该工具文档化形状的响应体，都会让该次尝试失败，而不会被当作完成调用或成功观测。响应体只要带有 `base_resp` 信封，该信封就必须包含有效的整数状态码；信封存在但无效——不是对象、缺少字段或值不是整数——即视为格式错误的响应，绝不会被当成信封缺失。收到的非成功状态码也不会被无法读取或被截断的响应体抹掉，因此响应体被截断的 429 仍会带着 `Retry-After` 切换 Key，而不会退化为通用的传输失败。

内置调用占用的恢复探测在整个尝试期间持有该 Key：无论上游调用持续多久，并发调用都会看到该 Key 处于忙状态；只有该尝试释放、结算或被丢弃时才会解除。未受保护的探测仍保留基于时间的恢复。当所有 Key 都已耗尽、处于冷却或正在被探测时，调用会以该原因失败，并且不会发出任何上游请求。

整次调用共享一个截止时间，受服务端超时约束，覆盖载荷准备、候选选择、反馈以及每次尝试；该截止时间不会因切换 Key 而重置。诊断信息只包含端点、Key 标签与尝试原因：凭据、鉴权头、图像载荷和查询内容都不会被记录。MCP 客户端收到的始终是固定诊断，只携带已知的状态码或 provider 码：provider 自身的消息、传输异常、trace 头、查询内容、图像来源以及所有已配置凭据（已启用、已禁用或旧的内嵌值）都不会出现在其中；原始失败会被直接丢弃，而不会作为错误来源附加、从而被调试格式化暴露出来。请求记录保存的也是同一段固定文案。
