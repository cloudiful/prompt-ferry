# Frontend asynchronous actions

[简体中文](frontend-async-actions.zh-CN.md)

Remote mutations use the shared `useAsyncAction` guard. The store or domain-action factory owns one guard instance per exclusion unit, and every entry point for that resource uses the same key. A held key returns `{ executed: false }`; UI handlers perform success-only effects—notifications, navigation, dialog close, and draft reset—only when `executed` is true.

Keep the key held through the mutation and required refresh. Capture record identity, selected owner, and submitted payload before awaiting. Propagate pending state to conflicting controls: disable their inputs and dismissal, keep unrelated resources usable, and show the spinner only on the action that started. Errors remain visible and drafts retryable. Do not create a component-local guard around a shared store action.

## Action coverage

- **Endpoint and model routes** — `endpoint:<id>` covers endpoint save/delete/toggle and OAuth device/browser start, each poll, completion, refresh, and clear. `modelroute:<id>` covers route save/delete/toggle. Probes use independent `networktest:<domain>:<id>` keys. Pending state reaches rows and the endpoint dialog. OAuth controls receive the store-owned callback through the page and dialog; each device poll claims separately, while human approval does not hold the key. Evidence: `endpoint-actions.gates.test.ts`, `endpoint-oauth.test.ts`, `use-endpoint-oauth-actions.test.ts`, `endpoint-oauth-status.test.ts`, `endpoint-oauth-device-flow.test.ts`, `endpoint-oauth-browser-flow.test.ts`, and endpoint page/SFC tests.
- **MCP servers** — `mcp:<id>` covers save/delete and `mcp:create` covers create; the catalog probe uses `mcptest:<id>`. Pending state reaches the row and dialog. Catalog edits are local drafts. Evidence: `mcp-store.test.ts`, `record-actions.gates.test.ts`, `record-actions.lifecycle.test.ts`, and `record-actions.sfc.test.ts`.
- **Users** — `user:<id>` covers save/delete/password reset; `user:create` covers create. Pending state reaches the user row/dialog and reset control. Evidence: `users-store.test.ts` and the record-action gate, lifecycle, and SFC tests.
- **Client keys** — `clientkey:<id>` covers label/save/delete/toggle; create uses a key scoped to the captured selected user. Pending state reaches the key row/dialog. Evidence: `api-keys-store.test.ts` and the record-action gate, lifecycle, and SFC tests.
- **Relays** — `relay:<id>` covers save/delete/reconnect. The owner pending map reaches row controls and the dialog; fields and dismissal stay disabled through the mutation and refresh, and only the originating action spins. Evidence: `relays-store.test.ts`, `relay-actions.lifecycle.test.ts`, `relay-actions.sfc.test.ts`, and `relay-session-guard.test.ts`.
- **Relay host** — `host:local` covers role/settings/restart as one host resource. The shared pending state disables conflicting controls, only the origin spins, and role/settings completion preserves fields edited after submission. Evidence: `relay-host-role.test.ts`, `relay-host-actions.lifecycle.test.ts`, `relay-actions.sfc.test.ts`, and `relay-session-guard.test.ts`.
- **Settings** — `setting:<resource>` covers each settings section; request-content logging and usage retention share `setting:rawRetention`. Both retention forms disable during a write and only the origin spins. Evidence: `settings-store.test.ts`, `settings-actions.gates.test.ts`, `settings-actions.lifecycle.test.ts`, and `settings-actions.sfc.test.ts`.
- **Redaction** — `redaction:rules` covers save and `redaction:preview` covers the non-persisting preview. Their pending feedback is separate; stale preview responses are ignored. Evidence: `redaction-store.test.ts` and the remaining-action lifecycle/SFC tests.
- **Config archive** — preview/apply share one wizard-scoped key; explicit export has its own read feedback. Confirmation, file validation, and retryable draft state stay in the wizard. Evidence: `config-archive-actions.test.ts` and the remaining-action lifecycle/SFC tests.
- **Billing** — `billingrule:<id>` is shared by rule save/delete/toggle; `billing:reprice` is separate. Evidence: `billing-store.test.ts`, `billing-actions.lifecycle.test.ts`, and `billing-actions.sfc.test.ts`.
- **Approvals** — `approval:<id>` is shared by approve/reject. The chosen action spins and its conflicting alternative disables. Evidence: `approvals-store.test.ts` and the remaining-action gate/lifecycle/SFC tests.
- **Usage maintenance and perspective** — `usage:maintenance` is shared by clear/prune; `usage:perspective` is independent and ignores stale overview results. The existing clear dialog remains the maintenance UI. Evidence: `request-records-store.test.ts`, `usage-actions.gates.test.ts`, `usage-actions.lifecycle.test.ts`, and `usage-actions.sfc.test.ts`.
- **Conversation routing** — `conversation:<id>` is shared by override save/clear and session-affinity reset. Same-conversation actions and dialog dismissal conflict; other conversations stay independent. Evidence: `usage-actions.gates.test.ts`, `usage-actions.lifecycle.test.ts`, `usage-actions.sfc.test.ts`, and `request-record-detail.test.ts`.
- **Authentication** — Worker login/logout and Relay-token login/logout use separate keys in their respective session stores. Busy spans each mutation and nested bootstrap; duplicate login cannot navigate or clear a form. Bootstrap/status reads do not clear a write claim. Evidence: `session-login.lifecycle.test.ts` and `relay-session-guard.test.ts`.

## Reads and UI conventions

Search, list, pagination, bootstrap, status, and quota reads keep their existing fetch state and stale-response rules; they do not use a mutation key. A follow-up read may stay inside its write callback when the action must remain pending through refresh. Local-only editor drafts do not receive fake network loading.

For an independent async read button, Nuxt UI `loading-auto` is appropriate when the handler returns the actual promise. It does not replace a domain-owned guard when multiple triggers can reach one mutation. Use one completion path and one notifier; a refused call must not duplicate a success toast. UI-only action work leaves public APIs and generated types unchanged.
