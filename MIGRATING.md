# Migrating to nodes

This is a fresh-destination configuration cutover, not a rolling upgrade and not an all-data history migration. The old PostgreSQL, encryption key, environment and volumes stay unchanged only as the rollback path; configuration is exported from the stopped source and imported into a new deployment, while normalized and raw request history stays with the old deployment. PostgreSQL 17 to 18 requires a supported dump/restore or pg_upgrade, never moving the data directory. Never put secrets in command arguments or logs.

1. Stop **all** old processes, including auto-restarting containers. Verify no live worker registry row or request lease remains. A running old deployment cannot be exported from and must not be upgraded in place.
2. Preserve the full old PostgreSQL dump, old encryption key, environment and volumes, and verify their restore before proceeding. This backup is the rollback path; history is not migrated into the destination.
3. Export the configuration from the stopped supported v1.43 source with the read-only maintenance command: `prompt-ferry maintenance export-config --out /secure/path/config.pfce --passphrase-file /secure/path/passphrase`. Supply the source URL and existing source master through a separate source environment; the command never rekeys, migrates or writes to the source and refuses while a worker registry row is live. The old global rekey tool remains code-supported, but it is not part of this cutover.
4. Create a separate destination environment selected with `PROMPT_FERRY_DOTENV`; do not rewrite the old file. Use flat `PROMPT_FERRY__*` names and review every value against the current configuration; the old `PROMPT_FERRY_RELAY__*` and `PROMPT_FERRY_WORKER__*` namespaces are rejected, not aliased. The destination needs PostgreSQL 18 with TimescaleDB 2.32.1 or newer and the TSL license preinstalled, and its master secret may differ from the source because import reseals the archived configuration. Give the destination its own empty Valkey deployment for coordination; do not flush an existing instance.
5. Boot the fresh destination normally without `--ack-stop-old-nodes`, import the archive through `POST /api/v1/admin/config-import/preview` and then `POST /api/v1/admin/config-import`, and verify login, restored users and configuration plus empty request history before reopening traffic.

From 1.44, raw request and response bodies are stored in PostgreSQL. The storage migration requires an empty raw-payload history: if the old deployment still holds raw payload rows, the normal schema upgrade refuses with a fresh-destination error and changes nothing. Use the fresh-destination cutover above in that case: configuration is restored from the archive, normalized and raw request history stays with the old deployment, and the operator alone cleans the old object store after review.

The current request family is an eight-hypertable TimescaleDB layout with one-day chunks and the native columnstore, so the database must run TimescaleDB 2.32.1 or newer with the TSL license (`timescale/timescaledb:2.32.1-pg18` or an equivalent installation). TimescaleDB 2.32.0 is refused before any gate or schema write, because its background jobs fail with portal errors in the compression policies, the continuous-aggregate refresh and the job-history maintenance. Upgrade the image first, then run `ALTER EXTENSION timescaledb UPDATE` to 2.32.1 in every database that has the extension installed, including `template1`, and only then start the new runtime; the node never upgrades the extension itself. The node refuses to start before writing a gate row, migration history or schema when the extension is missing or unsupported, and it never creates the extension itself. A database initialized with the older native-partition request family is refused as well, even when it is empty: export its configuration with the read-only maintenance command, create a fresh TimescaleDB database, run the normal bootstrap, and import the archive. No empty-database or acknowledgement inference turns an initialized legacy database into a fresh destination.

Closed day chunks are compressed by columnstore policy roughly 24 to 48 hours after their first row, not at a fixed age, because a day chunk is only closed after its following boundary. Recent chunks and rows stay uncompressed and keep the normal late-update, delete and partial-upsert behaviour. There is no retention policy in this layout; the runtime maintenance window decides which chunks are dropped. Metadata, normalized content and raw payloads have independent retention days: the tick drops whole expired chunks for the metadata parent and the six normalized content parents, while raw maintenance handles one raw chunk per transaction: it takes that chunk's `ACCESS EXCLUSIVE` lock and decompresses a compressed boundary chunk up front, locks and decompresses the paired metadata chunk by exact range, then either clears continuation metadata in that range and drops exactly one verified whole-old raw chunk, or deletes the boundary chunk's expired rows in bounded batches. Each raw chunk commits on its own, so the chunk lock, decompression and blocking cost are paid per chunk. The current UTC day chunk always survives maintenance. A full-history admin clear drops every chunk before the current UTC day across all eight parents and then deletes the remaining current-day rows; the reported `deleted` count covers only those bounded row deletes, not rows inside dropped chunks, and the chunk drop and row clear are not one transaction.

Request statistics are served from a one-minute continuous aggregate over the request family. The rollup is materialized by a one-minute policy over complete minutes, and a window that starts or ends inside a minute is answered from the raw rows, so sub-minute windows and the newest rows stay exact. A historical write into an already materialized minute becomes visible after that policy pass, not immediately; the policy schedule bounds the delay to about one minute. Deletes are immediate for statistics: a per-user or windowed clear refreshes the minutes it deleted before the call returns, and a retention chunk drop refreshes the minutes it carried away before maintenance returns. Every refresh stops at the database's current minute, so an incomplete current bucket is never materialized and a mutated row dated after the current minute keeps any already materialized bucket until the policy reaches that minute; no refresh advances the aggregate past the present. No in-process response cache masks these refreshes. Per-request percentiles such as p95 remain raw-row computations over the requested window and are never derived from rolled-up buckets.

A bounded clear is one READ COMMITTED transaction that holds the partition maintenance advisory key, captures the candidate envelope and referenced prompt-block hashes, then locks every chunk it can touch in ROW SHARE mode and decompresses the compressed ones before deleting any row. Because the request-family DELETE runs against already-decompressed chunks, the clear is not limited by `timescaledb.max_tuples_decompressed_per_dml_transaction`; the guard still applies to unrelated row DML. The transaction commits the family delete and the scoped deletion of only the candidate-related old prompt blocks together, and any failure rolls back both the deletes and the decompression, so the chunks return to their previous compressed state. The cost is proportional to the compressed rows and bytes in the touched chunks, not just the selected rows: expect the clear to last as long as decompressing those chunks, and expect the compression policy to recompress them after commit. The chunk locks are held until commit, so the policy cannot compress a touched hot chunk mid-clear and overlapping clears serialize instead of interleaving. See the cutover notes above for the operational sequence.

Use direct PostgreSQL connections or SESSION pooling only; transaction/statement pooling is unsupported. Do not run `DISCARD ALL` on application sessions. For subsequent newer versions drain and close all application sessions before the exclusive barrier and migration. Same-version nodes join without migration; downgrade is rejected. A failed or draining gate does not reset itself: use backups and manual recovery, not ad-hoc reset SQL. Do not expect cross-group in-memory takeover or transparent retry after generation has started.

Peers authenticate before the WebSocket upgrade, so both nodes of a star must run the same build. The peer link protocol changed: a node cannot link to a node of an older build, and the mutual hello frames inside the WebSocket are gone. The peer endpoint of a node is `GET /_internal/node` with the proof headers `x-prompt-ferry-peer-ticket` and `x-prompt-ferry-peer-proof`, and the challenge endpoint is `GET /_internal/node/challenge` on the same listener and port; no extra port, secret or setting is needed. The accepting node answers with `x-prompt-ferry-peer-confirmation` in the 101 response, and the dialing node checks it before it admits the peer or sends any business frame; the proof of the dialer alone never opens a link.

## Configuration archives

The encrypted configuration archive is a configuration backup, not a full backup. It carries the restorable configuration only: accounts with their password hashes, client keys, upstream endpoints with their API keys and OAuth tokens, model routes, MCP servers with their credentials and the personal MCP OAuth grants, redaction rules and the restorable worker settings. It carries no database schema, request history, raw request bodies, node identity or Valkey payload, so it is not a substitute for a PostgreSQL dump or a full backup. The target deployment provides its own Valkey connection and its own master secret. Raw request and response bodies are retained in PostgreSQL and are covered by the database backup.

### Exporting from a stopped old deployment

When the source must not be started or upgraded, produce the archive with the read-only maintenance command instead of the admin API:

```
prompt-ferry maintenance export-config --out /secure/path/config.pfce --passphrase-file /secure/path/passphrase
```

`--passphrase-stdin` reads the passphrase from standard input instead; a passphrase is never accepted as a command argument. The source URL and the source master secret come from the node configuration or the environment, exactly as for any other command. The command opens read-only sessions, holds the upgrade claim and the exclusive session barrier for the duration of the export, refuses while any worker registry row is live, and compares the configuration revision before and after reading. A source schema other than the supported v1.43 layout fails clearly; the export never migrates, downgrades, repairs, or writes to the source deployment. The archive is created with mode 0600 and an existing file is never overwritten. The passphrase follows the archive bounds (12 to 1024 characters), and only the archive's format, fingerprint, size, revision, and non-secret domain counts are reported. Import the result into the fresh deployment through `POST /api/v1/admin/config-import/preview` and then `POST /api/v1/admin/config-import`.

Personal MCP OAuth grants travel decrypted inside the archive and are sealed again with the destination master secret, so the source and the destination do not need to be the same. A restored grant starts a new connection epoch, and pending authorization states and refresh leases are never restored. An archive written before the personal MCP OAuth domain existed is still accepted and restores no grant; the import preview and the import report say so, and the affected servers may need reauthorization. Explicit per-user endpoint selections travel as their own domain, including a stored row whose endpoint is NULL (that means "use the routing default" and stays distinct from the absence of a row); the table's `updated_at` is cache bookkeeping and does not travel. An archive written before that domain existed restores no per-user preference and falls back to routing, with a preview warning.

An import replaces the restorable configuration inside one transaction. It first locks `users` and `client_keys` in SHARE ROW EXCLUSIVE mode, so concurrent identity writers wait while ordinary reads stay available, and it restores the archived client-key `created_at` instead of restamping it (a legacy archive without a timestamp keeps a current-time fallback). Before commit it reads the actual maximum identifiers and both sequence `last_value`/`is_called` pairs and restarts each sequence transactionally, preserving an advanced uncalled head and never rewinding; a failed import therefore leaves both identity heads and their called flags unchanged, and post-restore user and client-key creation continues above the imported identifiers.

The shared Valkey coordination row belongs to the deployment that runs the worker. A new export never contains it, an import keeps the destination row untouched, and an archive that still carries it ignores the archived value instead of applying it. Restore the coordination state of a deployment with its own operational procedure, not with a configuration archive.

An archive written while the billing feature existed still carries four retired MCP credential fields (`default_cost`, `strict_mode`, `billing_period_start`, `billing_period_end`). Those archives are read by the bounded format-2 compatibility reader, which verifies the original payload fingerprint before reshaping anything, discards the retired fields and never writes them into a current archive. A current export carries none of them, the retired database columns no longer exist, and the import preview reports the discarded fields by count only. The same reader discards the raw object-store configuration and the coordination settings of a format-2 archive and reports them by count; a hand-built current archive that tries to carry the raw object-store setting is rejected.

The archive format is versioned: container format 1 and snapshot payload format 3 are current. A current export declares ten portable domains: users, client keys, endpoints, model routes, MCP servers, MCP credentials, settings, per-user redaction configs, personal MCP OAuth grants and explicit per-user endpoint preferences. A format-2 archive declares its own nine- or ten-domain set and is verified and normalized to the current ten-domain form; a native format-3 archive written before the preference domain existed still imports with that domain empty and warns in the preview. A format-2 archive that predates the personal MCP OAuth domain restores no grant and says so in the preview. A domain set with an unknown, a duplicated or a missing current domain is rejected before anything is written, a declaration that omits the preference domain cannot carry preference rows, and a grant or preference whose parent is missing from the archive fails the import instead of being dropped silently.
