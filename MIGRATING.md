# Migrating to nodes

This is an all-data maintenance cutover, not a rolling upgrade. Preserve PostgreSQL users, configuration, history and raw payloads. Back up PostgreSQL, the old encryption key and environment, object storage, and all node/data/config volumes; verify restoration before proceeding. PostgreSQL 17 to 18 requires a supported dump/restore or pg_upgrade, never moving the data directory. Never put secrets in command arguments or logs.

1. Stop **all** pre-protocol processes, including auto-restarting containers. Verify no live registry or request leases remain. Acknowledgement never ignores live rows.
2. Create an isolated new environment file and select it using `PROMPT_FERRY_DOTENV`; do not automatically rewrite the old file. The old `PROMPT_FERRY_RELAY__*` and `PROMPT_FERRY_WORKER__*` namespaces are rejected, not aliases. Move applicable worker settings such as `DATABASE_URL`, `VALKEY_URL`, `UPSTREAM_API_KEY`, `MCP_WARMUP`, `MCP_OAUTH_REDIRECT_BASE`, and `RAW_OBJECT_STORE_*` to `PROMPT_FERRY__` names; use `PROMPT_FERRY__DATABASE_URL` for the database, `PROMPT_FERRY__BIND` for the listener, `PROMPT_FERRY__LOG_LEVEL` for logging and `PROMPT_FERRY_PORT` for the Compose published port. Remove old relay/worker tokens, bootstrap credentials, binds and relay URLs; peer URLs are `PROMPT_FERRY__PEER_URLS` JSON arrays. Review every old setting against the current configuration; not all old settings have replacements.
3. Simplest: reuse the old worker configuration encryption key as `PROMPT_FERRY__MASTER_SECRET`, provided it is the required base64 32-byte key and sharing it with all peers is an acceptable trust decision. Otherwise configure the new master and provide the old key through `PROMPT_FERRY_LEGACY_WORKER_CONFIG_ENCRYPTION_KEY` or `--legacy-key-file` (not both). Run `prompt-ferry maintenance rekey` for the dry run, then only after verifying it succeeds run `prompt-ferry maintenance rekey --apply --ack-stop-old-nodes` with the same key source. A file may be supplied as `--legacy-key-file /secure/path`. This covers all master-owned envelopes, including historical redaction sessions; decrypt errors or unsupported old schema fail all-or-nothing. Investigate rather than discarding data.
4. Start the first new node with `prompt-ferry --ack-stop-old-nodes` only when the legacy gate requires it. After the gate is established start normally. Verify setup, login, users, configuration and history before reopening traffic. Keep backups until verification is complete.

Use direct PostgreSQL connections or SESSION pooling only; transaction/statement pooling is unsupported. Do not run `DISCARD ALL` on application sessions. For subsequent newer versions drain and close all application sessions before the exclusive barrier and migration. Same-version nodes join without migration; downgrade is rejected. A failed or draining gate does not reset itself: use backups and manual recovery, not ad-hoc reset SQL. Do not expect cross-group in-memory takeover or transparent retry after generation has started.

Peers authenticate before the WebSocket upgrade, so both nodes of a star must run the same build. The peer link protocol changed: a node cannot link to a node of an older build, and the mutual hello frames inside the WebSocket are gone. The peer endpoint of a node is `GET /_internal/node` with the proof headers `x-prompt-ferry-peer-ticket` and `x-prompt-ferry-peer-proof`, and the challenge endpoint is `GET /_internal/node/challenge` on the same listener and port; no extra port, secret or setting is needed. The accepting node answers with `x-prompt-ferry-peer-confirmation` in the 101 response, and the dialing node checks it before it admits the peer or sends any business frame; the proof of the dialer alone never opens a link.
